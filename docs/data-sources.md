# Data sources and sample status

## Area comparison and provisional test area

**Jezero** has a particularly convenient documented path for a first sample: a USGS Astrogeology STAC collection of MRO/CTX stereo DTMs, each with related orthorectified image assets, plus published Jezero-specific CTX and HiRISE map products. The Mars 2020 landing region also has extensive image coverage. **Gale** has extensive public Curiosity-era map resources and rover imagery, but products we found quickly include mosaics with differing spatial registration; one Caltech page specifically warns that some Gale products are not registered to the global THEMIS IR mosaic and may offset from MOLA and rover paths. This is not a complete inventory comparison, but Jezero currently looks simpler for testing co-located layers.

**Provisional sample area:** 77.44–77.49°E, 18.42–18.47°N around the Perseverance landing point (18.4446°N, 77.4509°E; planetocentric, positive-east longitude and ocentric latitude). This is a search AOI, not a confirmed DTM footprint. Its purpose is to include the landing point in the catalog query; the script must still identify a real intersecting DTM footprint before any sample is claimed.

### CTX terrain and orthophoto characteristics from documentation

- **Instrument/product:** MRO Context Camera stereo-derived CTX DTM, generated with the Ames Stereo Pipeline; related orthorectified images are generated from the corresponding stereo data.
- **Collection metadata and credit:** [STAC collection record](https://stac.astrogeology.usgs.gov/api/collections/mro_ctx_controlled_usgs_dtms) identifies NASA as producer and USGS as processor/host, gives CC0-1.0, and links DOI 10.5066/P9JKVWR3. Suggested citation recorded there: Laura et al. (2023), *Mars Reconnaissance Orbiter (MRO) Context Camera (CTX) orthoimage generated using Ames stereo pipeline derived digital terrain models*.
- **Product IDs / item ID:** not yet available because no item was returned from a live query in this environment. Record the STAC item ID and asset keys from `sample-metadata.json` after a successful run; do not substitute a collection ID for a measured product ID.
- **Geographic coverage:** individual DTMs cover the overlap of a pair of CTX images; their footprint must intersect the AOI. The site footprint has not yet been queried. The service uses STAC item geometry for footprint discovery.
- **Projection / coordinates:** collection metadata describes Mars (2015) sphere, ocentric, equirectangular, central longitude 0°, with metre axes and planetocentric, positive-east longitudes. The product documentation describes Mars geoid/areoid heights. The selected STAC item's GeoTIFF CRS and axis conventions must still be read before calculating distance or slope.
- **Spacing and units:** CTX DTM documentation describes 20 m post spacing; collection metadata reports ground-sample-distance values from about 20 to 36 m across items. Elevation is in metres relative to the areoid. Posting/GSD is not the true resolving power: documented reliable feature scale is coarser (often roughly 10–20 image pixels), and expected vertical precision is about 3–5 m for typical parameters.
- **File format / actual file sizes:** analysis-ready Cloud Optimized GeoTIFFs are documented. Exact format, dimensions, size, bands and compression for the chosen item remain unknown until queried. The script streams only a bounded crop from each COG rather than downloading a full scene; if STAC provides `file:size`, it records the advertised full-asset size before reading.
- **Observation time:** tied to the CTX stereo pair. Exact acquisition times are item-specific and not yet queried.
- **NoData and quality:** CTX DTM documentation says areas without a good stereo topographic solution may be left out, producing holes and ragged edges. The exact item NoData value/mask has not been read. NoData means there is no output value at that cell; it does not establish a hazard or say what the terrain is. The optional intersection-error product is a processing diagnostic whose definition must be read before interpretation. It is not automatically a per-pixel uncertainty estimate. No interpolation has been inferred or assumed.
- **Registration:** a paired DTM and orthorectified image from the same item are the preferred combination. Their projected grids and transforms still need inspection. Separately controlled adjacent DTMs may have horizontal/vertical offsets and should not be mosaicked without checking.
- **Use / credit:** collection metadata reports CC0-1.0. Cite the product documentation and source acquisition/product IDs once known.
- **Limits for the proposed use:** not validated for astronaut safety or live navigation. A detailed orthophoto and a coarser DTM establish a difference in sampling/resolution, not by themselves a terrain error or unreliability. DTM artifacts, long-baseline tilt, stereo-matching holes, and 3–5 m typical vertical precision can affect short-baseline slope. A 20 m posting does not mean every 20 m feature is truly resolved.

## Reproducible sample procedure

Run `python scripts/fetch_mars_samples.py --bbox 77.44 18.42 77.49 18.47` in an environment with Python 3.10+, `rasterio`, `pyproj`, `numpy`, `matplotlib`, and network access. The script queries the USGS STAC search service, uses returned item asset `href`s (rather than fabricating raster URLs), and chooses one item that advertises a DTM and orthophoto GeoTIFF. It crops the same angular Mars ROI through COG range reads and crops an intersection-error raster only if one is advertised. It records source links, advertised full sizes, CRS, source/output spacing, scale/offset, NoData, dimensions and projected crop bounds; it checks bounding-box overlap and creates a PNG preview. The reprojection uses the Mars geographic CRS embedded in the raster metadata, not Earth's EPSG:4326 datum. It writes outputs under ignored `data/raw/jezero/`. This code path is not yet executed end to end, and asset-key naming remains an assumption to verify against live item JSON.

## What is and is not verified

The USGS collection metadata and docs, search route, broad coverage, CRS, GSD, licence, citation and known limitations were verified. Three `getent`/Python DNS checks fail for `stac.astrogeology.usgs.gov`, `astrogeo-ard.s3.amazonaws.com`, and unrelated `example.com`; `curl` reports “Could not resolve host” for the collection metadata URL. This points to the agent runtime's general DNS/network path, not a defect isolated to the data host. Separately, the web research tool successfully read the official collection metadata but could not fetch a parameterized search response; that tool-level API fetch failure is not evidence that the source API or a specific item is down. Local Python lacks `pip` and `python3-venv`; the attempted `.venv` creation failed before installation and its partial directory was removed. No catalog query, COG range read, raster inspection, item-specific metadata, advertised size, overlap check, quality asset, or PNG preview has succeeded. There is therefore **no successful NASA raster data test yet**. The script's live item selection, asset-key conventions, CRS transform behavior, and COG range reads remain to be validated in a networked project environment.
